# INF-TIMESTAMPER 実装計画

`docs/要件.md` を権威ある正本として、C# / .NET 8 / WPF による実装をフェーズに分割した計画書。

**役割**: Claude Code セッションが切れても次セッションが文脈を引き継げるようにする、進捗と「次にやること」の永続化。各フェーズの完了基準（DoD）を明文化する。

進捗を更新する際は、各フェーズの DoD のチェックを埋め、必要なら新しい派生タスクを追記する。

## 全体方針

- 要件.md と本ファイルが食い違った場合、**要件.md を優先**する（本ファイルは作業計画であり、仕様の正本ではない）。
- フェーズ境界では「ビルドが通り、テストが通り、最低限の実機確認ができる」状態を維持する。
- 大きな抽象化は使用箇所が出てから導入する（YAGNI）。例：「ゲーム抽象化」も MVP では INFINITAS 専用で書き、2 つ目のゲーム追加時に抽出する（→ Phase 9 で `Core/Games/` として実施済み）。

## プロジェクト構成

```
inf-timestamper/
├── InfTimestamper.sln
├── src/
│   ├── InfTimestamper/                  WPF アプリ本体（UI / ViewModel / DI 組立）
│   └── InfTimestamper.Core/             ドメイン層（UI 非依存。データモデル、状態機械、永続化、画像認識、OBS 抽象）
└── tests/
    └── InfTimestamper.Core.Tests/       xUnit テスト
```

- WPF プロジェクトは Core を参照する。Core は WPF を参照しない。
- 画像認識・OBS 接続・JSON 永続化は Core に置き、UI からはサービス境界経由で呼ぶ（テスタビリティと 2 台 PC 構成オプションの両立）。
- ViewModel は WPF プロジェクトに置く（`System.ComponentModel.INotifyPropertyChanged` の参照範囲を WPF 側に閉じる方が後々楽）。状態射影ロジックなど純粋計算は Core にも分離可能。

### Phase 8 — ゲーム検知の Reflux ファイル監視への移行

### Phase 9 — pop'n music 対応 — コード側完了

**ゴール**: `popn-lively-tracker` の出力ファイル監視によって、pop'n music のプレイをタイムスタンプ化できるようにする。INFINITAS 専用設計だった箇所に 2 つ目のゲームを通し、「ゲーム抽象化」を実使用箇所が出た時点で抽出する（全体方針の YAGNI に沿う）。

**入力仕様**: `popn-lively-tracker` の `docs/file-output.md`（互換契約としてキー名・書き出しタイミングが固定されている）。サンプルは `docs/sample/popn-tracker/`。

- `state.txt` — 1 行のみ。`選曲画面` / `プレイ中` / `プレイ終了` / `待機`。シーンが一時的に取れないときは直前の状態を保つ（`待機` に落ちない）
- `result.json` — プレイ終了を検知し譜面を特定できた時点で上書き。**リザルト画面の表示から数秒遅れる**（譜面特定にレコード表の更新を待つ。既定 20 秒でタイムアウト）
- 書き出しは `.tmp` → `os.replace` のアトミック方式なので、監視側が中途半端な内容を読むことはない

**着手前に決めた設計論点（ユーザ判断）**:

- **ゲーム選択はメインウィンドウのコンボボックス**。`初期状態` でのみ変更可能で、記録開始後はロック。選択は設定に永続化し次回起動時に復元。過去記録の読込時はファイルの `game` に自動追従

#### 実装上のハマりどころ

- **v2 の WebSocket には「プレイ開始」イベントが無い。** `nowplaying` は選曲画面（カーソル移動のたび）と
  曲決定画面の 2 箇所から飛ぶ。両者を分ける手がかりは payload の `images` だけで、選曲画面はジャケットしか
  入らず、曲決定画面はタイトル / レベル / BPM / エフェクター / イラストレーターの切り出し画像も入る。
  判定は `SdvxFieldMapper.IsSongDecided` に閉じてある。**SDVX Helper 側の `_broadcast_nowplaying` の
  呼び出し元が変わると壊れる**ので、実機で挙動が怪しいときはまずここを疑う
- **リザルトは本日分の全リザルト（`today_results`）で飛んでくる。** `items` の `timestamp` 最大のエントリを

  `JsonDocument` のまま必要なフィールドだけ読み、1 メッセージ 16MB を上限にしている
- `IPlayWatcher.Start(string directory)` が「ディレクトリ」前提だったため `Start(string source)` に汎化した。

#### α.1 の実機検証で判明したこと（→ α.2 で対応）

v1.2.0-alpha.1 を別 PC で動かした結果、「動くが 2〜3 回に 1 回記録されない」「リトライ時に記録されない」。
どちらも**プレイ開始の手がかりを曲決定画面の `nowplaying` だけに頼っていた**のが原因。

- リトライはリザルト画面から直接プレイに入るので、選曲も曲決定も通らず `nowplaying` が飛ばない
- SDVX Helper の画面判定が曲決定画面を取りこぼして `select → play` と直接遷移することがある
  （SDVX Helper 自身のトリガ表に `(select, play)` の組がある＝作者も想定している遷移）

対応: **SDVX Helper のログ `log/sdvx_helper.log` の `モード変更: X → play` 行を主のプレイ開始信号にした**
（`SdvxHelperLogTail`）。この行は画面遷移のたびに必ず書かれるので、どちらのケースでも拾える。
`nowplaying` は曲情報の補完（先に発火して `$title` 等を埋め、45 秒以内のログ遷移は同じプレイとして吸収）と、
フォルダ未設定時のフォールバックに残した。設定には「SDVX Helper のフォルダ」が増え、
`IPlayWatcher.Start` の引数は `WatchTarget`（`Directory` + `Endpoint`）のレコードになった。

ログ依存の弱点: 書式は `src/logger.py`、遷移名は `detect_mode` の enum 名で、SDVX Helper 側の変更で
壊れうる。壊れても `nowplaying` のフォールバックで α.1 相当の動作にはなる。
根本的には SDVX Helper 側の WebSocket に画面遷移（`mode`）の配信を足してもらうのが筋なので、
upstream への提案を検討する。

#### α.2 の実機検証で判明したこと（→ α.3 で対応）

「記録が二重で出る」「空の記録が出る」。**`init`（画面判定不能）を 1 つの画面として扱っていた**のが原因。

ユーザが `docs/sample/sdvx_helper/log/` に実機ログ（2026-09-23）を置いてくれたので解析したところ、
`SDVX Helper` の画面判定は暗転・演出・ロード中に頻繁に `init` へ落ちており、**遷移がほぼ全て `init` 経由**
だった（`select → play` / `detect → play` の直接遷移は 1 件も無く、`play → init` / `init → play` が
それぞれ 205 回）。つまり **1 プレイ中に `play → init → play` が何度も起きる**。

```
15:08:12 init → play      ← ここからが 1 プレイ
15:08:34 play → init
15:08:39 init → play      ← α.2 はここで 2 件目を作っていた
15:10:55 play → init
15:10:55 init → play      ← 3 件目
15:11:00 init → result_exscore
```

リザルトは 1 回しか来ないので、余ったエントリは `fields` 空のまま残る。これが「空の記録」。
実ログの 15:00〜17:30 では **`→ play` が 97 回 / 実プレイ 38 回**（`SDVX Helper` のリザルト登録 40 件 −
二重登録 2 件）。

対応:
- **`init` は状態として扱わず、直前の既知モードを保ったまま読み飛ばす。** 既知モードが `play` 以外から
  `play` に変わったときだけプレイ開始とする。実ログの抜粋を `docs/sample/sdvx_helper/mode-changes.log`
  に置き、プレイ開始の回数が `SDVX Helper` のリザルト登録数と一致することを回帰テストで固定した
- **`nowplaying` をプレイ開始のトリガから外し、曲情報のキャッシュに降格した。** 曲を決めてからプレイせずに
  戻ることがあるうえ、ログ側と二重に発火する時間窓ヒューリスティック（α.2 の `DuplicatePlayStartWindow`）が
  不要になる。**リトライでも直前の譜面の曲情報が入るようになった**のは副産物
- **`SDVX Helper` 自身の二重登録**（リザルト画面を 2 回読み取って同じプレイを 2 回登録する。実ログで
  15:02:50 と 15:02:51）に対して、譜面 + 成績の内容 + 30 秒の時間窓で同一判定して捨てる。
  登録ごとに `timestamp` がずれるので時刻では判定できない
- 原因を追えるよう、SDVX の検知経路と ViewModel のエントリ追加 / リザルトマージに INFO ログを入れた

#### 要件との突き合わせで見つかった実装漏れ（Phase 10 後半）

自動バックアップが丸ごと未実装だったことを受けて、`docs/要件.md` を全節点検した。
「仕様にあるが実装が無い／実装はあるが結線されていない」ものが 12 件見つかり、すべて対応した。

**実運用で踏むもの**
- **配信中にアプリを起動すると `配信開始待ち` から進めない**。`IObsConnection.IsStreamActiveAsync` は実装済みだったが production から一度も呼ばれていなかった。OBS の `StreamStateChanged` は変化時にしか飛ばないため、接続時点の実状態は自分で問い合わせる必要がある。`RecordingCoordinator.SyncStreamStateAsync` を追加し、接続確立（初回・再接続とも）のたびに突き合わせる。再接続時に配信が終わっていた場合の `記録終了` 遷移も同時に効くようになった
